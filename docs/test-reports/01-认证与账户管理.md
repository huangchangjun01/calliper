## 实现口径差异 / 发现的问题清单

1. **【缺陷·P1/P2】AUTH-012 超长用户名返回 500**：后端无显式用户名长度 binding，256 字符用户名通过校验后落入 DB varchar(50) 插入失败，返回 500 `failed to create user`，未满足"非法输入不 500"目标。建议增加 username 长度校验（如 ≤50）与邮箱格式校验。
2. **【差异】AUTH-028 第 3 种 Header 成因**：`extractToken` 使用 `strings.SplitN(header," ",2)`，"Bearer <token> extra" 会把剩余整串当作 token 传入，签名校验失败返回 401 `invalid or expired token`，而非文档预期的 `missing authorization token`。三种情况均 401 正确拒绝授权，仅错误文案/判断分支与预期不同。
3. **【环境口径】AUTH-001 等 admin 用例**：环境无 `admin/admin123` 账号，已用 `testadmin/pass1234` 替代；`data.username="testadmin"` 而非 "admin"。前端 Header 展示为登录输入用户名。
4. **【已知行为】AUTH-043**：后端 PUT /account/me 仅校验邮箱非空，不校验邮箱格式（not-an-email 成功保存）；格式校验仅存在于前端 antd rule。若产品要求服务端强校验应转为 400（待产品确认）。
5. **【已知行为】AUTH-044**：JWT 中间件与账户查询均不再校验 `is_active`，用户停用后已签发 token 仍可访问受保护接口（返回 status="disabled"），登录入口立即 401。若产品要求"停用即即时失效"则属缺陷（P2，待产品确认）。
6. **【基础事实】JWT 配置**：默认 secret 为 `change-me-in-production`、`JWT_EXPIRATION_HOURS=24`（.env 未显式设置，生产需配置强 secret，见 config.go 启动告警）。
7. **【说明】注册接口 DB 不可用文案**为 `database unavailable`，与登录接口的 `authentication service unavailable` 不同（AUTH-007 仅覆盖登录路径，未执行注册停库场景）。
